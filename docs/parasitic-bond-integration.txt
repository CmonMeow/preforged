The existing world tick advances player health in actor-ID order. Each
advance_health_locked call partitions its own conditions/regeneration boundaries.
A target's later expiry/removal callback can therefore find that the caster was
already advanced past the return's true timestamp. Simply calling a heal at
max(event_time,health_updated),or dropping a stale timestamp,is incorrect.

Before advancing an affected health cursor to T,process all due linked-return
boundaries <=T chronologically. Advance source/target to the boundary,consume
the ledger entry before callbacks,then apply actual healing/modifiers/death
cleanup before proceeding. Recursion guards must not lose pending returns.
Never revive a corpse with an overdue callback. Test both source/target ID
orders and sparse vs dense tick cadence; green single-actor expiry tests alone
cannot establish this behavior.

Required integration tests:
- Native20second degeneration and rank0/12/20 caster healing,cap/DeepWound/Defile.
- Same-caster renewal produces no immediate heal and only the renewed return.
- Target death/removal heals at the actual end event;caster death first removes
  outgoing hexes and all returns,without healing a corpse.
- Death/resurrection,leave/rejoin and reused IDs cannot inherit stale links.
- A delayed return before an otherwise lethal later degeneration slice can
  affect survival;simulate both ID orders and one long tick vs100ms ticks.
- Same-time deaths/returns need an explicit private-server ordering policy;
  do not claim unmeasured retail ordering.
- Cross-caster replacement must cover the documented double-heal anomaly;
  recipient/rank/timing still need evidence. The same-caster ledger API must
  reject being used as a substitute for that distinct operation.
- Player and combat NPC targets need expiry/removal/death integration.
- Casting gates,scoped target validation,1second activation,2second recharge,
  caster183 and target184 native body publication,cancel/interrupt and reconnect.
