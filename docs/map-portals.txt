Captured route expansion
------------------------
Another32 directed routes were added from transitions in the spawn/NPC logs.
The importer requires a matching local Wiki Exit(s) entry, both map navigation
meshes, walkable captured endpoints and a non-overlapping source trigger fully
inside one navigation cell. It skips manual travel requests, unknown map
adjacencies and unsupported geometry. The current importer is
tools/portals/import_captured_routes.py; it writes review artifacts under
build/reports/captured-portal-review before promotion.

These added endpoints are still marked travel_method unknown. Wiki adjacency
confirms the logical map connection, but cannot prove that the logged player
walked through that specific trigger. The trigger rectangles are provisional
developer bounds, and client traversal still needs live verification.

Captured direction-specific arrival positions and planes come from the actual
local transition capture. The Foibles reverse uses an explicitly generated
collision-connected development arrival. Both endpoint planes match the pinned 2022 navigation
assets. Wiki Exit(s) tables independently confirm each logical adjacency.
The capture records loading/map changes but marks travel_method unknown:
neither a recorded map change nor the shape of a DAT navigation cell proves
the retail zone trigger. Active rectangle geometry is explicitly developer
defined around those observed exit positions. Do not describe it as decoded
ArenaNet trigger geometry or a complete retail spawn-point catalog.

Validation proves the rectangle's entire area on its required plane. A small
gate uses convex-cell containment; a complete doorway may span several cells.
The latter uses exact trapezoid-union coverage within a genuine DAT neighbour
component, partitioned at all vertex heights and edge-order intersections.
Interval coverage at each partition proves every strip, rather than a grid or
four corners. Horizontal gaps larger than the existing0.01navigation tolerance
fail validation; an overlapping floor or unlinked cell cannot fill a gap.
Arrivals must be walkable on the stated destination plane and asset. Portal
transfers never fall back to a generic spawn or last logout point. Direct map
entry (/tp) uses the configured map spawn, then the map-center fallback
described in private-server-features.txt.
The FWNAV navigation portal field represents cross-plane cell connections;
it is not a map transition. No unknown FFNA chunk was treated as an exit.

Host integration
-----------------
1. Read Catalog::read(config_path / "map-portals.txt") once at host startup.
   validate_all(lambda map -> const navigation::Mesh*) before enabling it.
   The existing pinned map-asset resolver supplies each logical map's mesh.
   An error must be reported as an unavailable portal catalog, not swallowed.
2. Keep one Detector per world session. On initialized map entry/reposition:
   detector.reseed(catalog, Sample{map,plane,epoch,server_monotonic_ms,{x,y}}).
   This suppresses spawning inside a trigger; no movement means no transfer.
3. After each actual collision-accepted authoritative movement segment call
   detector.observe(catalog, sample, true). Call for every accepted route leg
   when the simulation resolves multiple legs in one update. Do not pass the
   requested click destination or an unvalidated CMSG position as the sample.
   Explicit position changes use reseed or authoritative_step=false.
4. A Crossing contains source/instance epoch, destination/asset, and the
   direction-specific Arrival{map,plane,point,facing}. Recheck campaign/map
   availability and character/session identity through the existing travel
   service. Freeze further movement while a crossing is pending; consume it
   using the existing map transfer flow, not a new bridge or client patch.
5. Store the arrival in the transfer grant and initialize the new player from
   it. Do not substitute map_spawn(), captured account logout coordinates or
   the selected character's old position. Transfer grants must retain plane
   and facing as well as x/y. All current captured arrivals use plane0.
6. Call detector.resolve(server_monotonic_ms) on either success or rejection.
   It applies the gate's cooldown; a failed gate also requires leaving and
   entering again. A new epoch reseed consumes any pending cooldown. Report
   rejected travel with gate ID/source/destination/epoch and actual reason.

The detector clips a swept segment against the rectangle, so movement does
not tunnel through a thin trigger. A positive traversal interval and crossing
the inward face in the outward direction are required. The transverse bounds
are closed so a valid outer navigation-edge lane still transfers. Walking
along the inward face, entering a transverse side without crossing that face,
a single corner contact, or moving backwards does not travel. A sample landing
exactly on the inward face cannot swallow the following crossing. The ending
plane must be the source gate's plane. A validated
DAT connector may change plane while entering, but changing floor while
already inside its XY footprint does not invent a crossing. Map/epoch changes,
clock reversal, invalid position, gaps>3seconds and jumps>900world units seed
a new segment rather than fabricate movement across unseen space. Time uses
the host's monotonic clock, never client time or a reset per-map clock.
